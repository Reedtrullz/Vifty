# Vifty Post-v1.4.8 Validation Workplan

**Date:** 2026-09-13

**Status:** Active

**Authority:** [docs/release-status.md](../release-status.md) and `.github/release-manifest.json` are the current release-fact authorities.

**Goal:** Validate the exact published v1.4.8 binary on the available supported MacBookPro18,1 before making installed-release, helper-parity, or manual fan-control claims. Keep the public compatibility record evidence-backed, then return to product polish.

## Current posture

- `v1.4.8` is the current published Developer ID release. Its public artifact, checksum, notarization, stapling, Gatekeeper, TeamID, and Homebrew handoff evidence passed at release time.
- Exact-build installed release review, signed-helper parity, explicit Auto restoration, and supervised Fixed/Curve compatibility remain pending for v1.4.8. Evidence from v1.3.2, v1.4.5, a local build, or CI does not transfer to this binary.
- `v1.1.1` remains the immutable source-first fallback. Do not retag it or refresh its unsigned-dev assets from later `main`.
- The lifecycle's v1.4.5 Auto-only helper admission is a narrowly scoped historical recovery fallback for that install line. Do not replace it with v1.4.8 by string substitution; admit a current helper only after exact-build parity and Auto-restoration evidence pass.

## Execution sequence

1. **Capture a read-only baseline.** Confirm the checkout, current manifest, disk guard, installed app identity, launchd/daemon state, and `viftyctl diagnose --json`. Preserve any blocked or stale recovery evidence.
2. **Bind the exact public archive.** Use the reviewed checkout's current `publishedRelease` and run the Developer ID readiness/artifact verification gates. Never choose a historical archive, candidate, URL, direct app path, or manually supplied SHA as a substitute for the manifest-pinned archive.
3. **Install through the reviewed transaction.** Use `make install-public-release PUBLIC_RELEASE_ARCHIVE=/absolute/path/Vifty-v1.4.8.zip` only after the archive passes the no-skip verifier. Do not raw-copy the app, call `sudo`, reset BTM globally, invoke direct helper commands, or bypass the replacement ledger.
4. **Prove runtime identity and helper parity.** Confirm the installed app version/build, TeamID, required component hashes, LaunchDaemon registration, daemon response, and exact installed daemon match. Keep fan control blocked until read-only readiness is safe.
5. **Prove Auto first.** Run the normal app/daemon Auto path and capture fresh daemon readback showing System-managed ownership, no manual marker, no recovery pending, and no cooling blockers.
6. **Run supervised hardware acceptance.** On the supported MacBookPro18,1 only, choose in-range values from a fresh daemon snapshot and exercise Fixed RPM, Temperature Curve, and final Auto restoration through the UI. Record requested-versus-effective targets, hardware mode/raw mode, selected sensor, timestamps, and every receipt/readback. The operator must remain present through all fan writes and final Auto proof.
7. **Collect and review evidence.** Run the read-only validation collector and the manual-smoke readiness/review gates. Only an exact-build report with explicit `passed-auto-restored` evidence may promote the v1.4.8 compatibility claim.
8. **Update public compatibility facts.** Change `docs/compatibility.md`, generated indexes, or release-status prose only from the reviewed evidence bundle. Keep other model rows as “Needs report.”
9. **Resume product polish.** After the validation boundary is closed, prioritize the small-window layout, helper-state clarity, menu-bar settings, local observability, and agent workflow improvements from the historical June plan. Sparkle remains a future signed-appcast/in-place-update project.

Minimum evidence commands for the supported-hardware pass:

```sh
make manual-smoke-readiness
make validation-evidence
make validation-evidence-review VALIDATION_EVIDENCE_REVIEW_MODE=supported-hardware
```

Run `make agent-run-smoke-evidence-current-build` only as a separate, supervised developer-workload proof after the same readiness gate passes.

## Safety boundaries

- Readiness and diagnostics are read-only; they never authorize fan writes.
- Never use `ViftyHelper setFixed`, `ViftyHelper auto`, raw SMC tools, unguarded `viftyctl prepare`, or a raw RPM write from an agent.
- Never retry a blocked or ambiguous replacement transaction by changing paths, deleting evidence, resetting the ledger, or selecting another archive.
- Keep source-first, local-ad-hoc, CI, historical-release, and current-public-release evidence separate.
- Keep telemetry local and in-memory; do not add accounts, analytics, cloud sync, or persistent rolling history.

## Definition of done

- The exact v1.4.8 app and daemon identities are installed and matched.
- Read-only diagnose is ready before any manual mode.
- Fixed and Curve each have confirmed daemon/SMC readback on MacBookPro18,1.
- Final Auto restoration is confirmed with no manual ownership or recovery pending.
- The evidence bundle is reviewed and the public compatibility record is updated only if the exact-build evidence passes.
- If any gate blocks, the blocker and evidence remain recorded and no compatibility claim is promoted.
